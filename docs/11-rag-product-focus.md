# RAG 核心能力与下一阶段执行规范

## 1. 产品定位

RAG Notes Agent 的核心不是“带聊天框的笔记应用”，而是“可验证的知识检索与回答工作台”：

```text
文档/笔记 -> 解析清洗 -> 结构化切块 -> Embedding + 实体关系索引
    -> Query Router -> 查询改写 -> 关键词 + 向量召回 -> RRF
    -> 关系/全局问题的 GraphRAG-lite 扩展 -> 噪声过滤/重排
    -> 证据约束生成 -> 引用与检索诊断
```

页面、接口和审计记录都应围绕这条链路组织。回答文本是最终产物，证据质量、召回覆盖率、
延迟和可解释性才是产品的核心竞争力。

## 2. 已实现的 RAG 闭环

- **路由**：`direct`、`memory`、`clarify` 问题跳过知识库，`rag` 问题进入检索；路由原因通过 SSE trace 公开。
- **策略响应**：高置信度的“你是谁”和“我是谁”由 `router-policy-v2` 固定响应，避免外部模型改写身份或生成伪引用。
- **灰区路由**：可选 Hybrid Router 只让 LLM 分类规则无法确定的问题；输出必须通过枚举、置信度和显式资料范围校验，失败默认进入 RAG。
- **索引一致性**：Embedding revision 与知识库 `index_status` 双重门控，模型切换后禁止混用旧向量。
- **混合召回**：关键词召回和向量召回分别排序，再使用 RRF 融合，避免不同分数量纲直接相加。
- **成本控制**：查询改写、查询向量、重排均支持 Redis 优先和内存 TTL LRU 回退，缓存失败不影响正确性。
- **质量保护**：候选噪声预过滤，Cross-encoder 失败时回退到确定性规则排序，不扩大知识库边界。
- **生成约束**：模型只能读取当前工作区/知识库证据；证据不足时拒答，回答引用快照可定位到原文。
- **可观测性**：记录关键词候选、向量候选、RRF 数量、重排数量、最终证据数和各阶段耗时。

## 3. 页面应如何凸显 RAG

1. 问答助手的“显示检索过程”只展示公开决策轨迹，不展示模型隐式思维；至少包含路由原因、查询改写、召回、重排、证据约束。
2. 研究页首屏固定展示 RAG 链路和当前检索器，查询完成后显示候选数量、缓存命中和阶段耗时。
3. 每条回答引用都能反向定位到文档块或笔记；证据面板展示来源类型、定位符和 Markdown 原文。
4. 设置页只暴露 LLM、Embedding、Reranker、Query Rewrite 等能力开关，不暴露数据库实现细节。
5. 评测结果与索引状态属于知识库工作流的一部分，后续应提供 Recall@K、MRR、Top1、噪声率和延迟趋势。

文章对照审查、已落地能力和未落地能力见 `docs/13-rag-enterprise-gap-analysis.md`。Evidence 预算基础版
已接入问答链路；下一阶段继续完成来源校验、分阶段 badcase 归因，再做双路召回、Dynamic Top-K、反馈
回流和有限步 Agentic RAG；暂不引入没有真实轨迹和标注数据支撑的 Query Rewrite/RL 训练。

## 4. 下一阶段实施顺序

### 4.0 场景审查与 GraphRAG-lite（已实现）

当前项目对单事实和同章节上下文已经具备可验收能力；多跳关系和全局归纳此前会退化为 Top-K
切块。本阶段加入实体、关系、切块关联索引，关系问题一跳扩展，全局问题文档覆盖采样，
并将图谱候选与 Hybrid 使用 RRF 合并。详细差距和验收指标见 `docs/12-rag-scenario-audit.md`。

### 4.1 Parent-Child Retrieval（已实现本地版本）

小块负责精确召回，生成时拼接同章节的父段落或相邻块；引用仍指向实际命中的子块，避免长文切块后上下文断裂。
实现要求：

- 使用 `document_id + ordinal + section` 限定上下文，不跨文档拼接。
- 父上下文有最大字符数和去重策略，防止 Prompt 膨胀。
- 诊断中分别记录子块候选数、扩展上下文数、上下文字符数和扩展耗时。
- 当前实现默认窗口为相邻 1 个块、单条证据最多 2,400 字符；生产环境可按模型上下文窗口调整。

### 4.2 Metadata Boost（已实现）

标题、章节和来源类型的轻量权重已抽象为独立策略，SQLite 和 PostgreSQL 检索器共享同一实现；权重来自环境配置，研究页显示加权候选数量。

在不改变工作区边界的前提下，对标题、章节路径、文档类型提供可解释的轻量加权；权重必须配置化并纳入离线评测，
不能用不可审计的常数掩盖召回退化。

### 4.3 生产索引（适配器与迁移已实现，生产回填待验收）

PostgreSQL + pgvector HNSW 与 FTS/GIN 作为生产实现，已接入 `PostgresHybridRetriever` 并保留当前 `Evidence` 契约；当前仍需在真实 PostgreSQL 环境完成双写回填、RLS、压测和回滚演练，不能把本地测试结果当作生产质量基线。
迁移必须支持双写/回填、版本切换、租户过滤和可回滚，不能直接替换 SQLite 全量扫描。

### 4.4 评测门禁

每次调整切分、Query Rewrite、Embedding、RRF 或 Reranker，都必须在固定评测集上记录：

- Top1、Recall@5、MRR
- 关键词覆盖率、噪声率、拒答正确率
- P50/P95 端到端延迟、缓存命中率

只有在核心指标不退化或有明确收益时才能升级默认策略；LLM Query Rewrite 和 Cross-encoder 的提升必须用真实配置测量，不能用模拟数据代替。
